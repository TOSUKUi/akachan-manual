# 0001. 男性向け赤ちゃんガイドの静的サイト

**Date**: 2026-08-14
**Status**: Accepted

## Summary

生まれる予定だけど何もわからない男性向けに、新生児期から 2 歳までの育児知識と手続きをまとめた静的サイトを作ります。東京都品川区在住の世帯を対象に、医療・制度情報は公式ソースで裏取りし、医学的エビデンスのある推奨は絶対に漏らさない構成にします。Vite で React をビルドし、章ごとの静的な HTML を出力して GitHub Pages で公開します。コンテンツは fact.md 形式の Markdown で管理し、元ソースへのリンクを必ず明記します。

## Context

このリポジトリ（akachan-manual）は現在スキル群以外何も入っていない、グリーンフィールドの状態です。既存のサイト「shinagawa-hojokin」は、品川区の妊娠・出産・産後の給付・助成を検証済みファクトシートとしてまとめたサイトで、このプロジェクトの姉妹にあたります。今回の依頼は、その「制度・お金」の話ではなく、**生まれた後の育児の実践知識**です。

対象読者は「男性で赤ちゃんが産まれる予定だが、よくわからない」人です。産まれるまでの制度は hojokin に任せ、このサイトは出産当日から 2 歳までの「どう動くか」「何をすればいいか」「何をしてはいけないか」に集中します。読者は慌てているので、最初の 1 画面で全体を把握でき、各章に飛んで詳細を読める構成が求められます。

医療・制度の情報は生命に関わります。医学的エビデンスが確立している推奨（SIDS 予防、予防接種、チャイルドシート、揺さぶり禁止など）を漏らすことは許されません。情報は AI がまとめるため、元ソースへのリンクを必ず付け、読者が一次情報を確認できるようにします。

技術面では、読者はスマホで読むことが多い想定です。SPA は避け、各章が独立した静的な HTML になる構成（SEO に有利）を選びます。デザインは hojokin と同じトーン（paper 背景、ティール系グリーン、Zen Maru Gothic 見出し）を shadcn/ui で再構成します。

## Requirements

**User stories**:
- パパ予定者として、出産当日の動き方（持ち物、産院での流れ、手続きの開始）を一発で把握したい。
- パパ予定者として、新生児のお世話の基本（抱っこ、沐浴、おむつ、ミルク、睡眠、SIDS 予防、頭の形）を知りたい。
- パパ予定者として、予防接種のスケジュールを漏れなく管理したい。
- パパ予定者として、健診で気になる症状（目の問題、耳、股関節、発達）の見分け方を知りたい。
- パパ予定者として、離乳食の開始タイミングと進め方、やってはいけないことを知りたい。
- パパ予定者として、事故・安全（誤飲、転落、やけど、窒息、チャイルドシート、溺水）の予防法を知りたい。
- パパ予定者として、やってはいけないこと（揺さぶり、はちみつ、うつぶせ寝など）と、しきたり・迷信の真偽を知りたい。
- パパ予定者として、産後うつのサインと相談窓口を知りたい。
- パパ予定者として、手続き（出生届、保険、助成、保育園）の早見と、詳細が載っている hojokin への誘導を得たい。
- パパ予定者として、全ページから検索して、気になる用語の該当箇所にすぐ飛びたい。

**Acceptance criteria**:
- **AC-1**: トップページに「最重要チェックリスト」があり、出産当日〜退院までと、新生児〜2 歳の育児で絶対に押さえるべき項目（出生届 14 日以内、予防接種スケジュール管理、仰向け寝、チャイルドシート、はちみつ 1 歳まで NG、揺さぶり禁止など）が 1 画面で確認できる。
- **AC-2**: サイトは 9 章構成で、各章が独立した静的な HTML ページとして出力される（SPA ではない）。章は「出産直前・当日の動き方」「新生児のお世話の基本」「予防接種スケジュールと管理」「健診と気になる症状」「離乳食」「事故と安全」「やってはいけないこと・しきたり」「パパの心構えと夫婦」「制度・手続きの早見」。
- **AC-3**: コンテンツは fact/ ディレクトリの章ごと 1 ファイルの Markdown（fact.md 形式）で管理され、フロントマターに title, slug, order, last_verified, sources を持つ。
- **AC-4**: 本文中の各事実に「根拠: [ソース名](URL)」が必ず付けられ、サイト上に表示される。根拠リンクの無い事実が fact にある場合、ビルドが失敗する。根拠 URL は frontmatter の sources[] に含まれることが必須（H2/H3 見出し単位で検証）。
- **AC-5**: 「絶対にやっておくべき」項目（医学的エビデンスが確立しているもの）には「必須」バッジが表示される。必須項目は frontmatter の `must: [stable_id]` で管理し、12 個の正規 ID（SIDS 予防、定期予防接種、チャイルドシート、揺さぶり禁止、誤飲・窒息予防、転落・やけど・溺水・熱中症予防、頭の形、目の問題、股関節脱臼チェック、はちみつ 1 歳まで禁止、うつぶせ寝・添い寝のリスク、産後うつのサイン）のうち、どれか一つでもどの章にも記載されていない場合、ビルドが失敗する。
- **AC-6**: サイト冒頭に「これは AI がまとめた内容であり、医療・法律アドバイスではない」旨の免責と、サイト全体の最終確認日（全章の last_verified の最大値）が表示される。
- **AC-7**: 全ページの共有ヘッダーに上部固定ナビ（章ジャンプ）と検索ボックスがあり、クライアント側で fact 全文（ビルド時に生成した search-index.json）を走査して該当箇所へジャンプできる。
- **AC-8**: ビルド成果物が dist/ に出力され、GitHub Pages で公開できる（GitHub Actions で gh-pages ブランチに配備）。リンクは相対パス（base: './'）で、サブディレクトリ（/akachan-manual/）でも正しく動く。公開ルートに .nojekyll を置く。
- **AC-9**: 制度・手続きの詳細（給付、助成、保育園申込）は hojokin（shinagawa-hojokin）へのリンクで誘導し、このサイト内で重複して詳細説明しない。hojokin の URL は設定定数（1 箇所）で管理する。
- **AC-10**: 各章ページに SEO メタデータ（title, description）が設定される。
- **AC-11**: fact の last_verified が 180 日を超えた章がある場合、ビルド時に警告を出す（医療情報の鮮度を担保）。

## Options considered

### Option 1: Next.js

React の定番フレームワーク。静的生成（SSG）で高速、shadcn/ui とそのまま組み合う。ホスティングは Vercel が定番。

**Pros**:
- shadcn/ui との相性が良く、エコシステムが大きい
- 静的生成が標準機能

**Cons**:
- ページ遷移も検索も要らないこの規模では、サーバ機能・ルーティング層が過剰
- Vercel 前提の運用になりがちで、GitHub Pages との相性が悪い

### Option 2: Vite + React（SPA モード）

Vite で React をビルドし、クライアント側ルーティング（React Router）でページを切り替える方式。

**Pros**:
- セットアップが最小
- 開発体験が速い

**Cons**:
- SPA は SEO に不利（ユーザーが明示的に「SPA だけはやめろ」と指定）
- 初回ロードが重くなる

### Option 3: Vite + React の静的マルチページ（vite-react-ssg）

Vite で React をビルドしつつ、ビルド時に各章を独立した静的な HTML として出力する方式（SSG 相当）。ページ遷移は通常のリンクで、SPA ではない。

**Pros**:
- ユーザー指定の「SPA 禁止」を満たし、SEO に有利
- 共通レイアウト（ナビ・フッター）を React コンポーネントで一度書けば全ページに反映
- GitHub Pages（静的ホスティング）にそのまま載る

**Cons**:
- vite-react-ssg は開発がやや停滞気味（メンテナンス状況を確認要）
- Next.js ほどのエコシステムはない

### Option 4: 素の Vite マルチページ（MPA）

各章に独立した entry HTML を置く方式。依存が最少。

**Pros**:
- 依存がほぼ無い
- 完全に静的な HTML

**Cons**:
- 共通レイアウト（ナビ・フッター）の管理が手書きになり、10 ページ以上で重複が増える
- fact.md の変換・ビルドの仕組みを自作する必要がある

## Decision

**Chosen option**: Option 3: Vite + React の静的マルチページ（vite-react-ssg）

Vite で React をビルドし、ビルド時に各章を独立した静的な HTML として出力します。SPA ではなく、ページ遷移は通常のリンクです。React はあくまでビルド前の言語として使い、最終出力は静的な HTML です。

**Implementation skills**: なし（このプロジェクトにインストール済みのコミュニティスキルで、この設計に直接関わるものはない）

## Rationale

エンジニアの指定（Vite + React、SPA 禁止、GitHub Pages、shadcn/ui）と、このサイトの性質（静的な長文ドキュメント、ページ遷移は章ジャンプのみ、検索はクライアント側で十分）を合わせると、vite-react-ssg が最適です。Next.js はこの規模では過剰で、GitHub Pages との相性も悪い。素の MPA は依存が最少ですが、共通レイアウトの管理が手書きになり、10 ページ超のサイトではメンテナンスコストが増えます。vite-react-ssg は React コンポーネントでレイアウトを一度書けば全ページに反映され、fact.md の変換もビルド時に自然に組み込めます。

注意点として、vite-react-ssg は開発が停滞気味とされるため、実装時（/develop）に最新のメンテナンス状況を確認し、必要なら同種の代替（例: vite の multi-page 設定 + 自前ビルドスクリプト）に切り替える判断を許容します。

## Feature design

**Data model sketch**:

fact.md のスキーマ（コンテンツの単一ソース。章ごと 1 ファイル、fact/ ディレクトリに置く）:

```yaml
---
title: "新生児のお世話の基本"    # 章の表示名
slug: newborn-care             # URL の一部。重複禁止
order: 2                       # 章の並び順
last_verified: 2026-08-14      # 最終裏取り確認日
sources:                       # この章で参照した公式ソース一覧
  - name: "品川区 妊娠がわかったときの届出"
    url: "https://..."
    checked: 2026-08-14
must: [sids, vaccines, carseat]  # 必須バッジを付ける項目の正規 ID
---
# 本文は Markdown。各節（H2/H3）の直下に
# 「根拠: [ソース名](url)」の形式で出典を必ず添える
# 必須項目には「必須」マーカー（例: ⭐ 必須: [id]）を付ける
```

- 各ファイルは frontmatter（title, slug, order, last_verified, sources, must）と本文 Markdown で構成
- slug は URL の一部になり、重複禁止
- sources は name, url, checked の配列。url は必須（AC-4）。本文の根拠 URL は必ず sources[] に含まれる（AC-4）
- must はこの章で「必須」バッジを付ける項目の正規 ID 配列（AC-5）。12 個の正規 ID は spec の付録に定義
- 本文中の「根拠:」行は、表示時にソースリンクとして描画される

**State transitions**:
該当なし（静的なコンテンツサイト。状態遷移なし）

**API surface**:
該当なし（バックエンドなし。全ページ静的な HTML）

**Value sourcing**:

| Action | Value produced / displayed | Source |
|---|---|---|
| トップページ表示 | 最重要チェックリストの各項目 | fact の frontmatter の must: [stable_id] に一致する項目 |
| 章ページ表示 | 章のタイトル、並び順 | fact の frontmatter（title, order） |
| 章ページ表示 | 章の最終確認日 | fact の frontmatter（last_verified） |
| 全ページ表示 | サイト全体の最終確認日 | 全章の frontmatter（last_verified）の最大値（AC-6） |
| 章ページ表示 | 根拠リンク | fact 本文の「根拠: [ソース名](URL)」行（sources と照合。URL は sources[] に含まれること） |
| 章ページ表示 | 必須バッジ | fact 本文の「必須」マーカー（id は frontmatter の must と一致） |
| 検索ボックス | 検索結果の該当箇所 | クライアント側で search-index.json（ビルド時に fact 全文から生成）を走査 |
| 全ページ | 免責文 | ビルド時に固定文言（テンプレートに定義） |
| 章ページ | 見出しアンカー | ビルド時に見出しから生成（検索ジャンプのターゲット） |
| 章ページ | SEO の title / description | fact の frontmatter（title）+ 章の冒頭文から生成（AC-10） |

**Key invariants**:
- 各 fact ファイルの slug は重複しない（ビルド時に検証）
- 「根拠:」の無い事実がある場合、ビルドが失敗する（AC-4）。根拠 URL は frontmatter の sources[] に含まれなければならない
- 必須カバレッジ 12 項目（正規 ID）は、必ずどこかの章に記載される（AC-5）。ビルド時に検証し、欠落があればビルドを失敗させる
- last_verified が 180 日を超えた章がある場合、ビルド時に警告を出す（AC-11）
- リンクは相対パス（base: './'）（GitHub Pages のサブディレクトリ配備に対応）。hojokin の絶対 URL のみ設定定数（config）で管理（AC-9）

**Security model**:
公開情報のみ。認証・認可なし。医療・制度情報を扱うため、サイト上に「AI がまとめた内容であり、医療・法律アドバイスではない。最終確認日と元ソースを必ず確認すること」の免責を表示する（AC-6）。コンプライアンススコープとしては、個人情報を扱わない（収集・保存しない）。

**Configuration required**:
- `BASE_PATH`（ビルド時）: GitHub Pages のサブディレクトリパス（/akachan-manual/）。相対パス生成に使用

**Critical test scenarios**:
- Happy path: トップページ → 最重要チェックリスト → 各章へリンク → 章ページで根拠リンク・必須バッジ・最終確認日が表示される、verifies **AC-1**, **AC-2**, **AC-4**, **AC-5**, **AC-6**
- Failure case: 根拠リンクの無い事実が fact にある → ビルドが失敗する、verifies **AC-4**
- Failure case: 必須カバレッジ 12 項目のどれかがどの章にも無い → ビルドが失敗する、verifies **AC-5**
- Failure case: 根拠 URL が frontmatter の sources[] に含まれない → ビルドが失敗する、verifies **AC-4**
- Failure case: last_verified が 180 日超の章がある → ビルドが警告を出す、verifies **AC-11**
- Auth/permission: 該当なし（公開サイト。認証なし）

## 付録: 必須カバレッジの正規 ID（AC-5）

12 項目の正規 ID と、対応する必須カバレッジの定義。fact の frontmatter `must:` と本文の「必須」マーカーは、必ずこの ID を使う。

| ID | 必須カバレッジ項目 |
|---|---|
| sids | SIDS 予防（仰向け寝、固めのマットレス、枕なし、タバコ煙回避） |
| vaccines | 定期予防接種の漏れ防止（スケジュール管理、品川区の助成） |
| carseat | チャイルドシート常時着用（乳児は後ろ向き） |
| no-shaking | 揺さぶり禁止（泣き止まない時の対処法） |
| choking | 誤飲・窒息予防（小さな物、コード、ビニール袋） |
| accident | 転落・やけど・溺水・熱中症予防 |
| head-shape | 頭の形（向き癖への対処、タミータイムは起きている時のみ） |
| eyes | 目の問題（斜視・弱視は早期発見が決め手） |
| hip | 股関節脱臼のチェック（おむつ替え時の開排） |
| honey | はちみつは 1 歳まで禁止（乳児ボツリヌス症） |
| sleep-risk | うつぶせ寝・添い寝のリスク |
| postpartum | 産後うつのサインと相談窓口 |

この 12 ID のうちどれか一つでも、どの章の fact にも記載されていない場合、ビルドが失敗する（AC-5）。

## Build plan

ビルドアプローチはプロジェクトに記録が無いため、エンドツーエンドのスライス（Tracer Bullet）を前提とします。各スライスが「コンテンツ → ビルド → 表示」を通して動くことを確認します。

1. Vite + React + TypeScript + shadcn/ui のプロジェクトを初期化し、vite-react-ssg で 1 ページ（トップ）が静的な HTML として出力されることを確認する、satisfies **AC-2**
2. fact.md のスキーマ（frontmatter + 本文）と、fact/ ディレクトリの雛形（9 章分の空ファイル + サンプル 1 章）を作る、satisfies **AC-3**
3. fact.md を読み込んで章一覧・章ページを生成するビルドパイプライン（frontmatter パース、Markdown 変換、slug によるページ出力）を作る、satisfies **AC-2**, **AC-3**
4. 共通レイアウト（上部固定ナビ、フッター、免責文）を React コンポーネントで作り、全ページに反映する、satisfies **AC-2**, **AC-6**, **AC-7**
5. 最重要チェックリスト（トップページ）を作る。出産当日〜退院までと、育児の必須項目を Badge 付きで一覧表示する、satisfies **AC-1**
6. 「根拠:」行の描画と、根拠リンク無しの事実をビルド時に検証して失敗させる仕組みを作る、satisfies **AC-4**
7. 必須カバレッジ 12 項目の存在をビルド時に検証する仕組みを作る、satisfies **AC-5**
8. 検索ボックス（クライアント側で search-index.json を走査し、該当箇所へジャンプ）を共有ヘッダーに作る、satisfies **AC-7**
9. GitHub Pages 配備の設定（dist/ 出力、base: './'、.nojekyll、GitHub Actions で gh-pages ブランチ配備）を作る、satisfies **AC-8**
10. 各章ページに SEO メタデータ（title, description）を設定する、satisfies **AC-10**
11. 9 章のコンテンツを fact 調査（公式ソース裏取り）に基づいて書き、全章を fact.md で実装する。fact 取得 → factcheck（公式ソース照合・URL 到達確認）→ 章に反映、の順で進める、satisfies **AC-1** 〜 **AC-11**
12. hojokin（shinagawa-hojokin）への誘導リンクを「制度・手続きの早見」章に配置する（URL は設定定数で一元管理）、satisfies **AC-9**
13. last_verified が 180 日超の章にビルド警告を出す仕組みを作る、satisfies **AC-11**

## Consequences

**Positive**:
- 読者はトップのチェックリストで全体を把握し、各章へ飛べる
- 医学的エビデンスのある推奨が漏れない（ビルド時に検証）
- 各事実に元ソースへのリンクが付き、読者が一次情報を確認できる
- 静的な HTML なので SEO に有利、GitHub Pages で無料公開

**Negative / tradeoffs**:
- vite-react-ssg は開発が停滞気味で、将来メンテナンスが必要になる可能性がある（代替への切り替え判断を許容）
- 章ごとに独立 HTML なので、コンテンツ変更のたびに再ビルドが必要
- hojokin に依存するため、hojokin 側の URL が変わるとリンク切れになる（定期的な確認が必要。URL は設定定数で一元管理）
- 医療情報の鮮度維持が必要。last_verified が古くなった章は警告が出るため、定期更新の運用が要る

**Neutral**:
- コンテンツは fact.md の Markdown で管理されるため、git の履歴・レビューが効く
